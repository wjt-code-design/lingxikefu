# 智能客服目标架构方案：从开环问答器到闭环学习系统

> 2026-08-29 · 基于 2026-08 评测攻坚（qa 90-95% 抖动带）与外部审查修复的完整实战沉淀
> 性质：目标架构（spec 级）——落地需按三期拆执行计划，本文不含任务级步骤

---

## 一、根本判断：系统的本质局限不是"答不准"

当前系统的问答质量已经打磨到位（CI 硬门禁 qa≥85% 实测 90-95%，refuse 100%，citation 98%+）。
继续在 prompt/检索上投入是边际递减的（批次 H 两轮实验实证：受控重放全绿也会在全量翻车，失败题池
只剩 band 边界与抖动题）。真正的问题是系统**不学习**：

1. **信号流失**：每次拒答、每次转人工、每次用户重复提问，都是"KB 覆盖不了真实问题分布"的证据，
   但这些信号只停在 admin_stats 的观测里，没有回流到知识生产。
2. **意图理解是词表的**：classify_intent 靠裸子串匹配，S2 事件实证其结构性缺陷——修词表是打地鼠。
3. **一致性无保障**：同 prompt 同资料 qa 抖动 ±2.5pp，失败题池逐轮轮转——评测里是抖动，
   产品里是"同一问题两次问答案不同"的投诉源。
4. **开环发布**：prompt/KB/代码改动直接上 master，靠离线评测事后守护，没有放量前的影子验证。

最优架构围绕一个主张展开：**把系统从开环问答器升级为闭环学习型客服系统**——
对话层负责答对，知识层负责越答越准，评估层负责一切变更不回退。

## 二、三层闭环架构

```
┌─────────────────────────── 对话层（实时路径，<3s）───────────────────────────┐
│                                                                              │
│  用户 ──► LLM 意图理解（一次调用，结构化输出）──► Router（消费结构化信号）      │
│              │ intent: qa|handoff|chitchat                                     │
│              │ risk_flag: 赔付/法律/投诉升级 → 强制人工                         │
│              │ topic_hint / entities ──► conv_state                            │
│         ├─ qa ──► RAG 管线（6 节点，不变）──► 答案                             │
│         │            ▲ 语义缓存（实体锁定 + kb_version 锚）                     │
│         ├─ 工具/建单/图片（现状保留）                                           │
│         └─ 降级话术三分：知识缺失≠系统故障≠场景未覆盖                            │
│  生成参数：temperature 0（一致性优先于多样性）                                  │
└──────────────┬───────────────────────────────────────────────────────────────┘
               │ 拒答/超时/澄清耗尽/点踩（结构化事件，非日志文本）
┌──────────────▼─────────── 知识层（T+1 运营闭环）─────────────────────────────┐
│  信号事件表 ──► 日聚类（重复问题自动归组）──► 周报（top N 未覆盖问题）          │
│                     │                                                         │
│                     ▼                                                         │
│  KB 补录工作台：草稿（人工撰写）──► 【发布门禁 = 全量评测跑新 KB】──►            │
│                     达标才递增 kb_version → 缓存自动失效                        │
│  知识三分：政策类（引原文）/ 运营类（易变）/ 长尾 Q&A 对（拒答回填主形态）        │
└──────────────┬───────────────────────────────────────────────────────────────┘
               │ 一切变更（prompt / KB / 模型 / 代码）
┌──────────────▼─────────── 评估层（质量护栏，已有资产扩维）────────────────────┐
│  单轮 100 题（现有）＋ 意图分类金标 ＋ 多轮组合场景 ＋ 拒答闭环有效性           │
│  （"上周拒答 top1 本周是否可答"——知识层 KPI 的度量即在此）                     │
│  变更放量：影子评估（shadow 流量对比）→ 全量门禁 → 放量                         │
└──────────────────────────────────────────────────────────────────────────────┘
```

## 三、关键架构决策（ADR 摘要）

### ADR-1 意图理解升级：一次 LLM 调用替代词表（对话层）

- **决策**：小模型（haiku 级/本地小模型）单次调用输出结构化 JSON：
  `{intent, risk_flag, emotion_level, topic_hint, entities}`。
- **为什么一次调用值得**：不只是替换词表——risk_flag（赔付/法律/升级投诉）直接驱动 Ticket Agent
  优先级与强制转人工，topic_hint/entities 喂 conv_state 槽位。一次调用补齐三个下游信号。
- **兜底**：LLM 超时/失败回落现有规则表（fail-open，已验证的模式）。
- **尺子**：口语化评测集（T9-S1 已建）扩为意图分类金标，CI 门禁新增 intent-accuracy。
- **成本**：每请求 +1 次小模型调用（~百 ms 级）；Router 的规则匹配本就零成本可并存。

### ADR-2 一致性工程：temperature 0 + 语义缓存（对话层）

- **决策**：generate 温度压至 0；answer_cache 从精确匹配升级语义缓存。
- **缓存命中四条件**（缺一不可）：语义相似≥阈值 + 实体锁定（已有防串答先例）+ kb_version 一致
  （已有全局锚）+ 意图一致。
- **取舍**：语义缓存引入"相似问题返回旧答案"的新风险面，由实体锁定与 kb_version 双锚控制；
  高抖动题（Q033/Q093 类）正是其收益区。
- **不做**：答案指纹强制一致（过度约束，同义改写是合理的）。

### ADR-3 降级话术三分（对话层，小改进高体验收益）

- 知识缺失（refuse）→"未收录，转人工"（现状）
- 系统故障（PipelineTimeout/向量库不可用）→"系统繁忙，请稍后重试"——用户会等待而非反复试探
- 场景未覆盖（clarify 耗尽）→ 引导补充信息
- 改动面：一个枚举 + 三段文案 + 事件类型字段。

### ADR-4 信号管道与 KB 发布门禁（知识层，本方案核心增量）

- **信号事件表**：refuse / pipeline_timeout / clarify_exhausted / 点踩，四类结构化事件入库
  （现有 audit 基建可复用），区分 KB 问题（前两类）与产品问题（后两类）。
- **日聚类周报**：embedding 向量聚类重复拒答 → top N 清单（hot_gaps 的升级版，从计数到内容）。
- **KB 发布走评测门禁**：补录草稿 → 人工审核 → 自动以新 KB 跑全量评测（qa/citation 不回退）
  → 达标递增 kb_version → 语义缓存自动失效。**把这两周建设的评测体系变成知识运营的基础设施**——
  防止"运营随手补一条错误 KB 把系统改坏"，与代码变更同权治理。
- **红线**：全自动 KB 生成不做——补录必须人审（客服场景错误承诺的合规代价远高于人力成本）。

### ADR-5 评估扩维与影子放量（评估层）

- 评测集扩三：意图分类金标（ADR-1 尺子）、多轮组合场景（改地址→查物流→投诉，conv_state 的
  回归保护）、拒答闭环有效性（上周拒答 top1 本周可答率——知识层 KPI）。
- 变更放量：prompt/模型变更先影子流量对比（新旧并行，diff 审计）再全量——当前 commit 直上
  master 的模式对 92-95% 抖动带的系统风险偏高。
- 判定规则升级（H 批次教训）：单轮抖动 ±2.5pp 不判回归，连续两轮趋势性下滑触发归因。

### 不做什么（与做什么同等重要）

- 不上 multi-agent 框架 / graph RAG——Router 前置 + 6 节点轻量管线的 YAGNI 判断依然正确
- 不做实时在线学习——KB 变更走版本化发布，可控可回滚
- 不微服务化——单机 FastAPI 的规模下是纯负担
- 不扩情绪词表——被 ADR-1 整体替代

## 四、演进路径（三期，验收用业务指标不用评测分）

| 期 | 内容 | 验收指标 |
|---|---|---|
| 一期·对话层加固 | ADR-1/2/3：LLM 意图分类 + temperature 0 + 降级话术三分 | 误转人工率 ↓；同题答案一致性 ↑；故障期重复提问率 ↓ |
| 二期·知识闭环 | ADR-4：信号事件表 + 聚类周报 + KB 发布门禁 | 拒答率周环比 ↓；拒答 top1 补录周期 ≤ 1 周 |
| 三期·扩维放量 | ADR-5：多轮评测集 + 影子评估 | 多轮任务完成率；变更回归捕获率 |

依赖关系：一期独立可做；二期的发布门禁复用现有 eval 体系（无阻塞依赖）；三期的影子评估
建议在一期稳定后启动。G2 挂账（M7/M5/L1）与一期同批顺路处理（同文件群）。

## 五、与现有资产的衔接（不推翻任何已建成的东西）

- `kb_version` 缓存失效锚 → 直接成为 KB 发布机制的技术底座
- 评测四件套 + CI 门禁 → 直接成为 KB 发布门禁与影子评估的判定器
- hot_gaps 观测 → 信号事件表的雏形（从计数升级为内容聚类）
- conv_state 槽位/主题 → ADR-1 结构化输出的消费方
- 规则式 classify_intent → 降级为 ADR-1 的 fallback（代码保留）
- S2/H 两轮实验的方法论（单变量、受控重放+全量双验证、抖动带判定）→ 全部沿用

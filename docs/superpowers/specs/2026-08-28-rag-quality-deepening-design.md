> 出发点：产品能力迭代——以运营/评测度量为基础，深化 RAG 回答质量
> 前置核对：2026-08-28 项目进度核对确认 T1/T2/T3 与多智能体架构均已落地（多份规划文档状态过时，本 spec 基于代码实况）

## 1. 背景与问题

### 1.1 评测基线现状（glm-4.5-air 时代，2026-08-26 冻结）

| 指标 | 当前 | 目标 | 缺口 |
|------|------|------|------|
| qa faithfulness | 82.1%（64/78） | ≥85% | -2.9pp |
| refuse 合理拒答 | 87.5%（7/8） | ≥90% | -2.5pp |
| 引用合法率 | **21.4%（3/14）** | ≥95% | **-73.6pp** |
| handoff / chitchat | 5/5、5/5 | — | 达标 |

已知失败点：Q064 双模型误拒答；引用合法率为最大缺口。

### 1.2 基线已失效（本规划的第一动因）

BASELINE.md 规定"四件套一致才可比"（评测集 + 判定脚本 + 检索参数 + 模型）。
自基线冻结以来：

1. **模型维度已变**：glm-4.5-air → LongCat-2.0（c0d9470 全面切换）
2. **判定脚本已变**：eval_faithfulness.py 引用统计偏置修复 + 诚实性判据收紧（ae0eb3b）
3. **prompt 已变**：引用贴原文、防自拒、并列结论逐条转述等多轮加固（52917d1、d850f78）

结论：旧基线数字与当前系统不可比，一切优化必须从重建基线开始。

### 1.3 目标与成功标准

- 三项指标在 LongCat 基线上达标：qa ≥85%、refuse ≥90%、引用合法率 ≥95%
- 引用合法率纳入 CI 硬门禁（与既有 faithfulness/拒答两项同款），指标只升不降有机制保障
- 每道失败题有归因记录，优化手段可追溯

## 2. 总体路线（三阶段）

### 阶段一：LongCat 基线重建（约 1 天）

| 步骤 | 内容 | 产出 |
|------|------|------|
| 1.1 | CI 手动入口 `workflow_dispatch full_eval` 跑全量 100 题 faithfulness（LongCat-2.0） | 三项指标快照 |
| 1.2 | 本地跑口语化评测集（口语化评测集.md，鲁棒性维度） | 口语化指标参考值 |
| 1.3 | 核实当前抽样 20 题在硬门禁下的 CI 状态（绿/红）；若红，说明抽样与旧全量基线存在代表性差异 | 门禁状态结论 |
| 1.4 | 逐题失败清单 + 每题一句归因（判据过时 / 检索未召回 / 生成不贴原文 / 引用格式问题） | 归因清单 |
| 1.5 | 更新 BASELINE.md / BASELINE.sha256：四件套 = 评测集 hash + 判定脚本 commit + RETRIEVAL_TOP_K=5 + LongCat-2.0；同步修正"先 report-only"过时说法 | 新基线冻结 |

**退出标准**：新基线数字冻结；每道失败题有归因分类。

### 阶段二：归因攻坚（3 个专项，每专项 1-2 天批次，按缺口排序）

**专项 1：引用合法率（21.4%→95%，最大缺口）**

根因假设按可能性排序（以阶段一归因结果确认，不预设）：

| 假设 | 判定特征 | 手段 |
|------|---------|------|
| H1 生成端格式问题（首选攻坚） | [来源N] 缺失/错位，或引用点句子为改写非原文转述 | qa_prompt.py 引用规则强化：few-shot 正例 + 禁改写要求（沿 52917d1/d850f78 先例） |
| H2 判定端过严（仅在证据充分时动） | 大量"实质支撑但交集 <30%"样本 | 调 bigram 窗口/交集阈值，**必须同步重冻结判定脚本版本** |
| H3 检索端缺料 | chunk 本身不含支撑句 | 并入专项 3 的检索层处理 |

攻坚顺序固定「先 H1 后 H2」，H3 只在有充分证据时动——prompt、判定器、检索三处禁止同时变化，保证归因单一变量。

**专项 2：拒答判据（87.5%→90%，含 Q064）**

- 从阶段一 refuse 失败题清单继续收敛（3e12323/ae0eb3b 已收敛过一轮自拒判据）
- 手段：`refuse.py` 判据与判定器 `_is_llm_refusal` **成对调整**——每次改动要么同时改两端，要么明确只改一端并在归因清单注明，防止"改回答"与"改判据"互相掩蔽

**专项 3：faithfulness（82.1%→85%）**

- 完全由阶段一失败题归因清单驱动，逐题修复后全量回归
- 已沉淀手段复用：并列结论逐条转述（d850f78）、禁止条款类推（ae0eb3b）、防自拒正例（3e12323）

### 阶段三：门禁补全与二次冻结（约半天）

现状修正（2026-08-28 核实）：eval job **已是硬门禁**（ci.yml `Eval gate (hard)`：faithfulness ≥85% + 拒答 ≥90%，抽样 20 题，418a61b 转硬）；BASELINE.md 中"先 report-only"的说法已过时。**引用合法率 ≥95% 尚未纳入门禁。**

| 步骤 | 内容 |
|------|------|
| 3.1 | 专项 1 达标后，把引用合法率 ≥95% 纳入 ci.yml eval job 阈值（与既有两项同款硬门禁） |
| 3.2 | 全量 full_eval 手动跑一次验证（约 1h），BASELINE 二次冻结（达标值成为新下限） |

## 3. 测试与验证纪律（贯穿全程）

1. **红测先行**：每道失败题先落成可复现断言（test_eval_faithfulness.py 已有测试基础）
2. **全量回归**：每专项收尾跑全量 100 题，任何指标下降即回退该批次（git bisect 定位）
3. **台账纪律**：每批次末亲测 junitxml 计数，不信任口头"通过"
4. **四件套变更留痕**：判定脚本或检索参数任何变动 → 当次更新 BASELINE.md 并注明旧值不可比

## 4. 不做的事（YAGNI）

- 不扩评测集规模（100 题与口语化集够用）
- 不接新模型/新评测 LLM（LongCat-2.0 刚稳定，避免再动四件套）
- 不动多智能体架构（已落地且不在本次范围）
- 不做检索参数大调（top_k=5 有降噪调参依据，已冻结）
- 不做前端相关改动（T3 已完成）

## 5. 风险与缓解

| 风险 | 影响 | 缓解 |
|------|------|------|
| 引用合法率 95% 目标在当前模型能力下过高 | 专项 1 长期不达标 | 以阶段一归因数据为准：若 H1 修复后仍 <60%，在 BASELINE.md 记录实证并提出目标修订建议（需用户确认，不自行降标） |
| LongCat 输出不稳定导致评测抖动 | 单次全量结果波动 | eval_one_retry 已有重试机制；关键批次跑两次取一致结果 |
| 判定器改动被质疑"改尺子凑分" | 指标可信度受损 | H2 类改动必须先展示"实质支撑但判不合法"的具体样本，且新旧尺子双跑对比留档 |
| 全量评测约 1h，迭代节奏变慢 | 攻坚效率低 | 开发期用失败题子集快跑（--sample 已支持），收尾才跑全量 |

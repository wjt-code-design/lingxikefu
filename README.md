# 灵犀 · 多租户 RAG 智能客服平台

一个面向电商客服场景的知识库问答系统。核心要求不是"能答"，而是：**每句话都能指出出自哪份文档的哪一段；指不出来，就必须说"我不知道"。**

全栈独立开发：后端 121 个 Python 模块 / 1.3 万行 / 854 个单测，前端 77 个组件 / 25 个单测 / 7 条 Playwright E2E，56 个 API 端点。

---

## 为什么值得看

大多数 RAG 项目止步于"接上了向量库"。这个项目的重心在另外两件事：**检索到底准不准**，以及**怎么证明它准**。

| 你可能想找的 | 在这里 |
|---|---|
| 双路召回 + 加权 RRF 融合 | `backend/app/services/retrieval_service.py` |
| 排序分与拒答分为什么要解耦 | `backend/app/services/steps/refuse.py` |
| 重排节点的位置契约与 fail-open | `backend/app/services/steps/rerank.py` |
| 100 题评测集与冻结口径 | `eval-and-samples/` |
| 冻结哈希校验（防判定脚本被改后 CI 恒绿） | `scripts/check_baseline_hashes.py` |
| 纯 AST 多租户过滤门禁 | `scripts/check_tenant_filters.py` |

## 检索链路

```
用户输入
  → 意图分类（规则式；闲聊 / 转人工直接短路，不检索不调模型）
  → 查询改写
  → 两级缓存（命中则零模型调用直接返回）
  → 混合检索：dense(24) + sparse(24) → 加权 RRF(k=60, 2:1) → top 5
  → 重排（Rerank，5 进 5 出，只换顺序不动集合）
  → 拒答判定（dense 原始余弦分 < 0.30 → 拒答）
  → 带引用生成（SSE 流式）
```

**两个关键设计**：

1. **双路召回**：纯向量检索在型号、专有名词这类硬匹配上会失效，所以加一路字符级 bigram 稀疏匹配（不依赖中文分词）。融合时两路分值不是一个尺子、无法相加，改用 RRF 只比名次。
2. **排序分与拒答分解耦**：RRF 融合分没有绝对语义（理论上限约 0.049），不能当阈值。所以排序用融合分，拒答用 dense 原始余弦分。重排节点在拒答之前，但按原索引回填 chunk、`dense_score` 原样保留，因此**重排不影响拒答语义**。

## 评测：怎么证明它准

这是本项目最花力气的部分。

- 自建 100 题忠实性评测集，逐条标注"正确答案应出自哪份文档的哪一段"，含 8 条"这题不该答"的诚实性拒答题
- 自动判定脚本判三件事：答案对不对、该拒的拒没拒、引用的段落是否真能支撑结论
- **冻结四件套**：评测集 / 判定脚本 / 检索参数 / 模型 / 评测知识库 —— 任一改动，跑出的数就不可比
- 三个指标接进 CI 当硬门禁

当前全量基线（2026-10-27，qwen3.8-flash + rerank 开启态）：

| 指标 | 值 | 门禁 |
|---|---|---|
| 问答正确率 | **97.5%**（78/80） | ≥ 85% |
| 拒答准确率 | **100%**（8/8） | ≥ 90% |
| 引用合法率 | **100%**（256/256） | ≥ 95% |
| errors | **0** | 有上限门禁 |

重排效果（90 题确定性实测，零 LLM 成本）：

| 指标 | 重排前 | 重排后 |
|---|---|---|
| top-1 命中率 | 80.0% | **88.9%** |
| MRR | 0.8735 | **0.9333** |
| recall@5 | 98.8% | 98.8%（**不变，这是正确结果**） |

> recall@5 不变不是 rerank 没用：它量的是"期望来源有没有进 top-5 集合"，而重排只重排集合内成员。**用 recall 衡量 rerank 是常见错误。**

复现：`backend/experiments/compare_rerank.py`

## 快速开始

```bash
# 1. 启动依赖（PostgreSQL 16 / Redis 7 / Qdrant）
cd backend && docker compose up -d

# 2. 后端
python -m venv .venv && .venv/bin/pip install -r requirements.txt
cp .env.example .env        # 填入你的模型 API Key
alembic upgrade head

# 3. 前端
cd frontend && npm install && npm run dev
```

向量化默认走**本地** `BAAI/bge-base-zh-v1.5`（768 维，零调用成本、数据不出境），不配 Key 也能跑通检索。

## 关于中文文件名

`eval-and-samples/kb/` 与 `backend/scripts/demo_data/` 下的中文文件名**刻意保留**，不做英文化。

原因：它们是冻结口径的一部分。判定脚本硬编码读取 `评测问题库.md`，评测集的"期望来源"列直接以文档名（如 `退换货政策`）与数据库 `doc_title` 做前缀匹配。改名会同时破坏冻结脚本哈希、评测集标注与守卫测试，使基线不再可复现。

## 已知边界

诚实说明这个项目**没做**什么：

- 没有微调 / 自训练模型，纯 RAG + 工程化路线
- 没有 HyDE，查询改写是规则层
- 意图分类是规则式关键词匹配，不是分类模型（LLM 版本在跑影子模式，尚未切流）
- 重排当前是 5 进 5 出：候选上限配了 24，但检索侧已先截到 5 条，所以"筛选"能力未启用
- 多租户是**架构能力**，不是运营规模——没有真实企业客户数据
